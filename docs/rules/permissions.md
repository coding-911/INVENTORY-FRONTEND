> 🔐 누가 어떤 API를 호출할 수 있는지와, 같은 API 안에서 권한에 따라 달라지는 규칙을 모았다. API별 원본은 [API 목록](https://app.notion.com/p/421b82ca31e581898e3fe58ea8d40ecb)의 "권한" 칸이고, 인증 방식은 [API 명세서](https://app.notion.com/p/408b82ca31e580d19b7ee382dacd572b) 1.3절이다. 둘이 다르면 API 목록 행을 고치고 이 페이지를 다시 맞춘다.

> 🔁 **2026-11-26 역할·권한 체계를 바꿨다.** 예전: 계정마다 역할 하나(관리자·입력자·조회자) + 금액 권한 0~2개. 지금: **권한 13개를 독립적으로 정하고, 역할은 권한을 고른 묶음이며, 계정은 역할 하나를 갖는다.** `USER_MANAGE` 권한자가 역할을 만들고 고칠 수 있고, 처음에는 기본 역할 6개를 만들어 둔다. 확정 사항 #106, ISS-1.

## 1. 권한 체계

### 1.1 설계 원칙

1. **권한은 서로 겹치지 않는다.** 동작 하나는 권한 하나에만 속한다. 한 API 안에서 내용에 따라 다른 동작(예: 7일보다 지난 날짜로 입력)은 그 부분만 다른 권한에 속한다.
2. **따로 주거나 뺄 일이 실제로 있는 단위로 나눈다.** API마다 권한을 두지 않는다(예: "거래처 등록만 되고 수정은 안 되는 사람"은 없다). 따로 떼어도 결국 같은 힘이면 떼지 않는다(역할을 고칠 수 있으면 자기 역할에 아무 권한이나 넣을 수 있으므로 계정 관리와 역할 관리는 하나다).
3. **로그인한 사람이면 누구나 하는 것은 권한으로 만들지 않는다.** 모든 조회(금액·계정 정보·감사 자료 제외), 내 정보, 본인 비밀번호 변경, 내 알림, 홈, 내가 낸 승인 요청 보기, 로그인·로그아웃.
4. **묶는 것은 역할이 한다.** 권한은 "무엇을 할 수 있나"만, 역할은 "누가 무엇을 맡나"만 책임진다.

### 1.2 권한 13개

| 코드 | 이름 | 범위 |
|---|---|---|
| `PARTNER_MANAGE` | 거래처 관리 | 거래처·담당자 등록·수정·삭제 |
| `PRODUCT_MANAGE` | 제품 관리 | 제품 등록·수정·삭제 |
| `MASTER_MANAGE` | 기준 정보 관리 | 품목군·창고·위치·통화·구성 묶음 관리, 제품 사용 중지·다시 사용 |
| `DOCUMENT_MANAGE` | 거래 문서 관리 | 프로젝트·거래 문서 등록·수정·확정·취소·삭제, 비교·복사, 첨부 올리기·떼기 |
| `STOCK_OPERATE` | 재고 처리 | 입고·출고·이동·검수·배정·납품·반품·교체·대차·실사·수리·보증, 처리 취소·정정, 폐기·대여 출고 요청 |
| `STOCK_ADJUST` | 재고 조정 | 재고 조정, 초기 재고 넣기, 기준일 이전 등록(납품 장비·처리 수량) |
| `APPROVE` | 승인 | 승인·반려·사후 확인, 승인·확인 대기함 전체 보기 |
| `CLOSING` | 마감 | 월 마감·해제, 거래 품목 잔량 마감 |
| `RECORD_CORRECT` | 기록 정정 | 확정된 기록 바로잡기: 7일보다 지난 날짜, 실사 중 범위 처리, 확정 문서의 프로젝트·거래처 변경, 이력 있는 제품의 Item Code 변경, 납품한 장비의 시리얼 변경, 정산 방식 바꾸기 |
| `AUDIT_VIEW` | 감사 조회 | 정합성 점검 결과 보기·지금 실행, 통합 변경 이력, 제품 변경 이력 |
| `USER_MANAGE` | 계정·역할 관리 | 계정 목록·하나·만들기·수정·삭제, 비밀번호 초기화, 역할 만들기·수정·삭제 |
| `COST_VIEW` | 금액 보기 | 응답의 금액 필드, 금액 이력·부대비용·마진·평가액 조회, 첨부 열기·내려받기 |
| `COST_EDIT` | 금액 수정 | 단가·부대비용·대여료·초기 재고 단가 넣기·고치기·비우기 |

권한 목록은 시스템이 정한다(마이그레이션으로 넣고 화면에서 추가·삭제하지 않는다). 코드에서 권한을 검사하므로, 권한을 더하려면 코드를 함께 바꿔야 하기 때문이다.

### 1.3 권한별 근거

| 권한 | 왜 따로 있나 | 왜 이 범위로 묶나 |
|---|---|---|
| `PARTNER_MANAGE` | 거래처 정보는 영업·구매 쪽에서 따로 맡을 수 있다 | 담당자는 거래처에 딸려 있어 따로 줄 일이 없다 |
| `PRODUCT_MANAGE` | 제품 등록은 일상 업무지만 거래처·문서와 맡는 사람이 다를 수 있다 | 등록·수정·삭제를 나눠 줄 일이 없다 |
| `MASTER_MANAGE` | 기준 정보는 바꾸면 여러 업무에 영향이 가서 드물게, 책임자가 바꾼다(예전 "관리자만") | 모두 거의 바뀌지 않는 코드 표·구조다. 제품 사용 중지도 제품 목록에서 빼는 일이라 같은 성격이다 |
| `DOCUMENT_MANAGE` | 프로젝트·거래 문서는 재고 처리와 맡는 사람이 다를 수 있다(문서는 영업·구매, 재고는 창고) | 프로젝트는 거래 문서를 담는 그릇이고, 첨부는 거래 문서의 증빙이다 |
| `STOCK_OPERATE` | 물건을 실제로 움직이는 일이다 | 입고부터 납품·대차·실사까지 같은 창고 업무 흐름이다. 실사만 따로 맡는 사람은 없다고 보고 나누지 않았다(2026-11-26) |
| `STOCK_ADJUST` | 처리 근거 없이 재고 숫자를 바꾸는 일이라 일상 처리와 분리한다(예전 "관리자만") | 셋 다 "원장에 근거 없는 수량을 넣는 일"이다 |
| `APPROVE` | 다른 사람의 요청을 승인하는 일이다. 승인만 하는 팀장 같은 역할이 생길 수 있다(ISS-1) | 승인·반려·사후 확인과 대기함 전체 보기는 같은 사람이 한다 |
| `CLOSING` | 기간이나 품목을 잠그는 일이다 | 월 마감과 잔량 마감은 모두 "더 이상 받지 않음"을 정하는 일이다 |
| `RECORD_CORRECT` | 확정된 기록을 바로잡는 일이라 일상 처리와 분리한다 | 대상 영역은 달라도 "확정된 것을 바꾼다"는 같은 책임이다. 영역마다 나누지 않는다: 금액은 7일 제한이 없고 월 마감으로만 막히므로(#103) 금액 쪽 정정 권한이 따로 필요한 경우가 없다(2026-11-26) |
| `AUDIT_VIEW` | 조회지만 시스템 전체의 변경 기록·점검 결과라 감사 책임자만 본다(예전 "관리자만") | 모두 "누가 무엇을 바꿨나·어디가 어긋났나"를 보는 자료다. 점검 실행은 업무 데이터를 바꾸지 않는다 |
| `USER_MANAGE` | 권한을 나눠 주는 권한이다. 이것이 있으면 다른 모든 권한을 얻을 수 있다 | 계정 관리와 역할 관리는 같은 힘이라 나누지 않는다 |
| `COST_VIEW` | 금액은 볼 수 있는 사람을 따로 정한다(COST-04) | 첨부를 막는 이유가 증빙에 금액이 있어서다(INV-86) |
| `COST_EDIT` | 금액을 넣고 고치는 사람을 따로 정한다(COST-04) | 금액 네 종류를 나눠 줄 일이 없다 |

### 1.4 두 권한을 함께 요구하는 동작

한 동작이 두 권한의 범위에 걸치는 것이 아니라 두 조건을 함께 거는 것이다. 겹침이 아니다.

| 동작 | 조건 | 이유 |
|---|---|---|
| `RECORD_CORRECT`의 모든 동작 | 그 영역의 권한 **그리고** `RECORD_CORRECT` | 정정은 그 업무를 할 수 있는 사람이 한다. 예: 7일보다 지난 날짜로 출고 = `STOCK_OPERATE` 그리고 `RECORD_CORRECT` |
| 거래 문서 품목 단가, 부대비용 | `DOCUMENT_MANAGE` **그리고** `COST_EDIT` | 문서·프로젝트를 다루는 사람이 금액을 넣는다 |
| 대여료 | `STOCK_OPERATE` **그리고** `COST_EDIT` | 대차를 다루는 사람이 넣는다 |
| 초기 재고 단가 | `STOCK_ADJUST` **그리고** `COST_EDIT` | 초기 재고를 넣는 사람이 단가도 넣는다 (INV-74) |

### 1.5 역할

- 계정은 역할을 **하나** 갖는다. 계정이 가진 권한 = 그 역할의 권한.
- `USER_MANAGE` 권한자가 역할을 만들고, 이름·설명·권한을 고치고, 지울 수 있다. 코드는 만든 뒤 바꾸지 않는다.
- 역할 이름 규칙(기본 역할): 앞말은 하는 일, 뒷말은 **운영자**(업무를 처리함) 또는 **사용자**(보기만 함). 코드는 큰 구분이 앞, 세부가 뒤(`OPERATOR_BASIC`)다.

**기본 역할** (마이그레이션으로 처음에 만들어 둔다)

기준: 예전 체계(역할 3개 × 금액 권한)가 허용하던 조합을 빠짐없이, 그리고 그것만 옮긴다. 예전에 할 수 있던 것이 사라지지 않게 하고, 문서에 없는 역할을 지어내지 않기 위해서다.

| 코드 | 이름 | 권한 | 근거 |
|---|---|---|---|
| `ADMIN` | 관리자 | 13개 전부 (고정) | 예전 관리자 정의(입력자의 일 + 승인·확인, 잔량·월 마감, 기준 정보, 계정 관리, 7일보다 지난 날짜). 금액 권한을 포함하는 이유는 R1 |
| `OPERATOR_BASIC` | 일반 운영자 | `PARTNER_MANAGE` `PRODUCT_MANAGE` `DOCUMENT_MANAGE` `STOCK_OPERATE` | 예전 입력자 정의(일상 처리, 거래 문서·거래처·제품 등록) |
| `OPERATOR_COST_VIEW` | 영업 운영자 | 일반 운영자 + `COST_VIEW` | 예전 입력자 + 금액 보기 |
| `OPERATOR_COST_EDIT` | 정산 운영자 | 일반 운영자 + `COST_VIEW` `COST_EDIT` | 예전 입력자 + 금액 수정(#73·#81) |
| `USER_BASIC` | 일반 사용자 | 없음 | 예전 조회자(보기만). 조회는 권한이 필요 없다(1.1의 3) |
| `USER_COST_VIEW` | 회계 사용자 | `COST_VIEW` | 예전 조회자 + 금액 보기(#105) |

운영자 역할에 `MASTER_MANAGE`·`STOCK_ADJUST`·`APPROVE`·`CLOSING`·`RECORD_CORRECT`·`AUDIT_VIEW`·`USER_MANAGE`가 없는 것은 예전 입력자에게 없던 일이기 때문이다. 이것만 맡는 역할(예: 승인만 하는 팀장)은 문서에 없어 기본으로 만들지 않았고, 필요하면 `USER_MANAGE` 권한자가 만든다.

### 1.6 역할 규칙

| 번호 | 규칙 | 오류 | 근거 |
|---|---|---|---|
| R1 | 관리자 역할(`ADMIN`)은 항상 13개 권한을 모두 갖고, 고치거나 지울 수 없다. 나머지 기본 역할은 처음에 만들어 둘 뿐 고치고 지울 수 있다 | `ROLE_LOCKED` | 관리자 역할에서 계정 관리를 실수로 빼면 아무도 복구할 수 없다. 금액을 빼는 것도 의미가 없다: 계정 관리가 있으면 금액 보기가 있는 계정을 만들 수 있다 |
| R2 | 사용 중인 관리자 역할 계정은 한 명 이상 남아야 한다. 자기 역할·사용 여부는 바꾸지 못하고 자기를 지우지 못한다 | `USER_LAST_ADMIN`, `USER_SELF_CHANGE` | INV-80 |
| R3 | `COST_EDIT`이 있는 역할은 `COST_VIEW`도 있어야 한다 | `ROLE_COST_EDIT_WITHOUT_VIEW` | 금액을 보지 못하면서 고칠 수는 없다 (INV-88) |
| R4 | 역할은 그 역할인 계정(삭제된 계정 제외)이 없을 때만 지울 수 있다 | `ROLE_IN_USE` | 계정은 역할이 반드시 있어야 한다 |
| R5 | 계정의 역할을 바꾸면 그 계정의 세션을 끊는다. 역할의 권한을 바꾸면 끊지 않고 다음 요청부터 적용한다 | — | INV-80. 권한은 요청마다 DB에서 읽는다(API 명세서 1.3) |

예전 규칙 "조회자에게는 금액 수정을 주지 못한다"(#105, INV-87, `USER_VIEWER_COST_EDIT`)는 없앤다. 금액 쓰기는 1.4처럼 영역 권한을 함께 요구하므로 업무 권한 없이 `COST_EDIT`만 있으면 어차피 고칠 수 없다.

### 1.7 공통

- 권한은 서버가 요청마다 DB에서 읽어 검사한다(세션에는 사용자 ID와 로그인 시각만 있다). 화면에서 숨기는 것은 편의일 뿐이다.
- 비밀번호 변경이 필요한 사용자(새 계정·초기화 직후)는 내 정보·본인 비밀번호 변경·로그아웃만 쓸 수 있다. 나머지는 403 `PASSWORD_CHANGE_REQUIRED` (API 명세서 1.14, #100).
- 권한이 없으면 403 `FORBIDDEN`, 로그인하지 않았으면 401 `UNAUTHENTICATED`.

### 1.8 이 페이지와 API 목록의 조건 표기

| 표기 | 뜻 | Spring Security 예 |
|---|---|---|
| **모두** | 로그인한 사용자 누구나 | `authenticated()` |
| 권한 코드 (예: `STOCK_OPERATE`) | 그 권한이 있음 | `hasAuthority('STOCK_OPERATE')` |
| A **그리고** B / A **또는** B | 둘 다 / 둘 중 하나 | `hasAuthority('A') and hasAuthority('B')` |

**구현**: 각 모듈의 컨트롤러 메서드에 `@PreAuthorize`로 위 조건을 붙인다(예: 통화 추가 `@PreAuthorize("hasAuthority('MASTER_MANAGE')")`). 권한 규칙이 그 API 코드 옆에 있어 모듈마다 스스로 관리하고, user 모듈의 보안 설정이 모든 경로를 알 필요가 없다. 역할(`hasRole`)로는 검사하지 않는다. 역할은 관리자가 바꿀 수 있는 묶음일 뿐이기 때문이다. 요청 본문 형식 검사가 권한 검사보다 먼저 돌아서, 권한 없는 사람이 형식이 틀린 본문을 보내면 403이 아니라 400이다. 업무 규칙 검사(API 명세서 1.10)보다는 항상 먼저다. 4절처럼 내용에 따라 달라지는 권한은 서비스에서 검사한다.

| project, importing(첨부) | 모두 | `DOCUMENT_MANAGE` |
| inventory, allocation, delivery, loan, equipment | 모두 | `STOCK_OPERATE` |
| cost | 금액 조회 `COST_VIEW`, 통화 목록 모두 | 금액 쓰기는 1.4, 통화 `MASTER_MANAGE` |
| user | 내 정보·역할·권한 목록 모두, 계정 `USER_MANAGE` | `USER_MANAGE` (본인 비밀번호 변경은 모두) |
| admin | 내 알림, 내가 낸 요청 모두 | 승인 `APPROVE`, 감사 `AUDIT_VIEW` |
| trash | 모두 | 1.4·3.4 |
| dashboard | 모두 | — |

3절에 없는 API는 위 기본 조건을 따른다.

## 3. 기본과 다른 API

### 3.1 별도 권한이 필요한 API

| 권한 | API | 메서드·경로 | 근거 |
|---|---|---|---|
| `USER_MANAGE` | 사용자 목록·하나, 계정 만들기·수정·삭제, 비밀번호 초기화 | `/api/v1/user`, `/user/{id}`, `/user/{id}/password-reset` | INV-80, 1.14 |
| `USER_MANAGE` | 역할 만들기·수정·삭제 | `POST /api/v1/user/role`, `PATCH·DELETE /user/role/{id}` | 1.6 |
| `STOCK_ADJUST` | 재고 조정, 초기 재고 넣기 | `POST /api/v1/inventory/adjustment`, `/opening` | INV-63, INV-55·58 |
| `STOCK_ADJUST` | 기준일 전 납품 장비 등록 | `POST /api/v1/equipment/pre-cutover-delivery` | INV-56 |
| `APPROVE` | 승인, 반려, 확인 | `POST /api/v1/admin/review/{id}/approve·reject·confirm` | INV-62·77 |
| `CLOSING` | 월 마감 하기·해제 | `POST /api/v1/inventory/period-closing/{period}/close·reopen` | INV-46·78 |
| `CLOSING` | 거래 품목 잔량 마감 | `POST /project/trade-document/{id}/line/{lineId}/close` | INV-28 |
| `STOCK_OPERATE` 그리고 `RECORD_CORRECT` | 정산 방식 바꾸기 | `POST /api/v1/loan/{id}/settlement-method` | INV-43 |
| `AUDIT_VIEW` | 정합성 점검 결과 목록, 지금 실행 | `/api/v1/admin/integrity-check`, `/run` | INV-78 |
| `AUDIT_VIEW` | 변경 이력 조회(통합), 제품 변경 이력 | `GET /api/v1/admin/change-history`, `GET /product/{id}/change` | INV-53·72 |

### 3.2 조회지만 내용이 권한에 따라 다른 API

| API | 메서드·경로 | 규칙 |
|---|---|---|
| 승인·확인 대기함 목록, 요청 하나 | `GET /api/v1/admin/review`, `/review/{id}` | 모두 호출할 수 있다. 자기가 낸 요청만 보이고, `APPROVE`가 있으면 전부 보인다. 남의 요청 하나를 열면 404 |
| 삭제 목록 | `GET /api/v1/trash` | 모두. 부대비용(`EXTRA_COST`)은 `COST_VIEW`가 있어야 보인다 |

### 3.3 금액 권한으로 막는 API

| API | 메서드·경로 | 조건 |
|---|---|---|
| 금액 변경 이력, 부대비용 목록·하나, 프로젝트 금액·마진, 창고 재고 평가액 | `GET /api/v1/cost/change`, `/cost/extra-cost…`, `/cost/project/{projectId}/margin`, `/cost/stock-valuation` | `COST_VIEW` |
| 부대비용 넣기·고치기·삭제, 거래 문서 품목 단가 | `POST·PATCH·DELETE /api/v1/cost/extra-cost…`, `PATCH /cost/trade-document/{id}/line-price` | `DOCUMENT_MANAGE` 그리고 `COST_EDIT` |
| 대여료 | `PATCH /api/v1/cost/loan-fee/{loanDocumentId}` | `STOCK_OPERATE` 그리고 `COST_EDIT` |
| 초기 재고 단가 | `PATCH /api/v1/cost/opening-cost` | `STOCK_ADJUST` 그리고 `COST_EDIT` (INV-74) |
| 첨부 파일 열기·내려받기 | `GET /api/v1/importing/attachment/{id}/content` | `COST_VIEW` (INV-86) |
| 통화 목록 | `GET /api/v1/cost/currency` | 모두 (금액이 아닌 코드 표) |

### 3.4 응답에 금액 필드가 섞이는 API

호출은 기본 조건(모두)이고, `COST_VIEW`가 없으면 금액 필드를 빼고 응답한다(INV-83, 개발 컨벤션 3절). 거래 문서 목록, 거래 문서 하나, 대차 문서 하나(대여료).

### 3.5 삭제한 것 복구

`POST /api/v1/trash/{entityType}/{id}/restore`는 **그 대상을 삭제하는 API와 같은 권한**이 필요하다. 예: 거래처는 `PARTNER_MANAGE`, 품목군·창고·위치·구성 묶음은 `MASTER_MANAGE`, 첨부는 `DOCUMENT_MANAGE`, 부대비용은 `DOCUMENT_MANAGE` 그리고 `COST_EDIT`. 지울 수 있는 사람이 되살릴 수 있어야 권한이 겹치지 않는다.

## 4. 같은 API 안에서 권한에 따라 달라지는 규칙

API를 호출할 수는 있지만 내용에 따라 추가 권한이 필요한 경우다. 서비스에서 검사하고, 막히면 403 `FORBIDDEN` 또는 표의 오류 코드로 돌려준다.

| 대상 API | 규칙 | 근거 |
|---|---|---|
| 업무 날짜가 있는 모든 업무 동작 | 오늘부터 7일 전까지만. `RECORD_CORRECT`가 있으면 마감되지 않은 달이면 된다. `STOCK_ADJUST` 동작(조정·초기 재고·기준일 이전 등록)은 원래 지난 날짜로 넣는 일이라 7일 제한이 없다. 미래 날짜는 모두 안 된다 | INV-15·16, `BUSINESS_DATE_TOO_OLD` |
| 제품 수정 | 이력 있는 제품의 Item Code 변경은 `RECORD_CORRECT`, 사유 필수 | INV-72 |
| 거래 문서 수정 | 다른 프로젝트·거래처로 옮기기는 `RECORD_CORRECT`. 기준일 이전 처리 수량 입력(첫 마감 전)은 `STOCK_ADJUST` | INV-55, #28·#49 |
| 장비 시리얼·메모 수정 | 고객에게 납품한 적 있는 장비의 시리얼은 `RECORD_CORRECT`. 확인된 시리얼을 바꾸면 누가 고치든 같은 트랜잭션에서 사후 확인 요청이 생긴다 | INV-61·77, #59 |
| 발주 없이 입고, 대차 기한 바꾸기 | `STOCK_OPERATE`로 하지만 사후 확인 요청(`APPROVE`가 처리)이 함께 생긴다 | INV-77, #9·#72 |
| 폐기 요청, 대여 출고, 동급 모델 정산, 실사 제출(차이 있음) | `STOCK_OPERATE`로 요청하고 `APPROVE`로 승인해야 원장·장비가 바뀐다 | INV-41·62 |
| 실사 중 범위의 일반 처리 | 막힌다. `RECORD_CORRECT`가 있으면 예외로 처리할 수 있고, 그 제품은 재실사 대상이 된다 | INV-48 |
| 완료된 거래 문서 | 메모는 `DOCUMENT_MANAGE`, 금액은 `DOCUMENT_MANAGE` 그리고 `COST_EDIT` | INV-67 |
| 계정 만들기·수정·삭제 | 1.6의 R2 | INV-80 |

## 6. 테스트

- API마다 "권한이 있는 사람은 성공", "그 권한만 없는 사람은 403" 테스트를 하나씩 둔다. 테스트 계정은 역할이 아니라 필요한 권한만 넣은 역할로 만든다(기본 역할 이름에 기대지 않는다).
- 1.4의 두 권한 동작은 둘 중 하나만 있는 경우 403을 각각 확인한다.
- 금액 필드 테스트: `COST_VIEW` 없이 3.4절 API를 부르면 JSON에 금액 키가 없어야 한다(INV-83).
- 권한 목록: DB(`auth.permissions`)와 코드의 권한 목록이 같은지 테스트한다.
